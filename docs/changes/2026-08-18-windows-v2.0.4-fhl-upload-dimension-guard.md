# Windows V2.0.4 FHL 图生图参考图长边保护

## 批次目标

- 诊断 FHL Images 图生图出现 `Invalid image file or mode for image 1` 是否由 8K 附近像素边界导致。
- 只为 Windows V2.0.4 的浏览器 FHL Images / Responses 图生图增加上传副本保护。
- 原图、受管媒体和历史记录保持不变；不修改 APIMart、RunningHub、Android、V2.0.3 或发布物。

## 真实边界测试

测试使用同一张程序生成的非透明 JPEG、同一提示词、`gpt-image-2`、FHL Images `/v1/images/edits`、`1024x1024` 输出和当前本机质量/格式配置。每次只提交一张，顺序执行，不使用批量、并发或自动重试。

| 上传长边 | 实际像素 | 文件大小 | 结果 | 响应证据 |
| --- | --- | ---: | --- | --- |
| 7999 | 7999 x 5333 | 303,543 B | 成功 | 完整 `data[0].b64_json` |
| 8000 | 8000 x 5333 | 300,878 B | 成功 | 完整 `data[0].b64_json` |
| 8192 | 8192 x 5461 | 314,324 B | 成功 | 完整 `data[0].b64_json` |
| 8193 | 8193 x 5462 | 302,186 B | 成功 | 完整 `data[0].b64_json` |

首次直连被本机 Windows 证书吊销检查以 `CRYPT_E_REVOCATION_OFFLINE` 阻止，HTTP 状态为 `000`，没有到达 FHL，不计入尺寸结论。随后只对这四个测试请求使用 `curl --ssl-no-revoke`，四次均得到完整成功结果。API Key、完整请求头和生成图片数据没有写入文档或 Git。

结论：本轮没有复现 8K 附近的尺寸失败，原错误不能认定为单纯的 `8000px` 边界，也可能来自源图格式、透明通道、模型或 Images 编辑兼容性。按已批准规则，只要 `8192px` 成功，浏览器保护值固定为 `8192px`；不继续扩大上限。

## 实现结果

- `remote-kernel/common.ts` 增加 FHL 图生图专用预处理：每张参考图在请求前读取真实像素尺寸。
- 长边超过 `8192px` 时按比例生成白底 JPEG 上传副本，使用现有 `0.82` 质量；原 data URL、历史对象和受管媒体文件不改写。
- `preparedBase` 只保留其原有的普通压缩豁免，不能绕过 FHL 长边检查。
- 尺寸未超限时继续使用原有按文件字节数触发的上传压缩策略；不会放大或重复缩放安全尺寸图片。
- 解码、Canvas 或 JPEG 编码失败时，在 `fetch` 前抛出本地错误，不向上游发送无效图片。
- FHL Images 和 FHL Responses 图生图共用保护；APIMart、RunningHub、提示词优化、图片反推和 Android 原生 HTTP 不进入该逻辑。
- 自动缩放时任务进度和日志记录原始/副本像素尺寸，例如：`12000x6000 -> 8192x4096`，不记录 Key、完整路径或图片内容。
- 安全尺寸内仍出现同类 400 时，提示格式、透明通道、模型或 Images 编辑兼容性，不继续盲目缩小或自动重试。
