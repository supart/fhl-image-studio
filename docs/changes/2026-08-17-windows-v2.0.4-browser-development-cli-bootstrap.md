# Windows V2.0.4 浏览器开发任务代理启动修复

## 问题与根因

- 用户在 Codex 浏览器提交文生图后收到 `后台任务代理不可用：缺少 runtime\cli\gptcodex-image.exe`。
- 失败发生在本地 CLI 启动前，没有进入 FHL API；历史失败记录保留为现场证据。
- 外层浏览器启动器只检查 Node、npm 和 Vite，`platform-vite` 的 Windows 开发分支也直接启动 Vite，因此全新开发目录不会准备浏览器任务代理。

## 实现

- 新增 `scripts/ensure-development-cli.mjs`，从 `product-version.json` 读取 `2.0.4 / V2.0.4` 并使用与发布链一致的 ldflags 构建 CLI。
- 脚本对 `product-version.json`、`go.mod`、可选 `go.sum` 和全部 Go 源码计算 SHA-256 摘要；CLI 与摘要状态都存在且匹配时跳过构建，源码或版本变化时自动刷新。
- Windows `npm run dev:windows` 固定执行 `版本检查 -> 开发 CLI 准备 -> Vite`；CLI 准备失败时立即停止，不再留下“页面能打开、提交才失败”的开发环境。
- 外层 `一键启动V2.0.4-Codex浏览器UI.cmd` 增加 Go 环境预检和明确提示；冷启动时发现并修复批处理混合换行导致的 CMD 解析问题，最终统一为 UTF-8 BOM + CRLF。
- `runtime\cli\gptcodex-image.exe` 和 `.gptcodex-image.development.json` 都是被忽略的本地开发产物，不复制旧版本二进制，也不进入提交。

## 自动化与冷启动

- 新增开发 CLI 行为测试：缺失时构建、摘要相同时跳过、Go 源码变化后重建、构建失败时不写成功状态。
- 新增 Windows 开发启动顺序测试：成功路径严格为 `version -> cli -> vite`，CLI 失败时 Vite 不启动。
- 真实冷启动前将本轮生成的 CLI 和摘要移为可恢复的忽略备份；外层启动器随后从完全缺失状态自动生成 `V2.0.4` CLI，Vite 6.4.2 在 `127.0.0.1:5173` 启动。
- CLI 只运行离线 `--status --json` 验证产品身份；没有提交图像任务或调用上游 API。

## 验收结果

- 前端 Node `603/603`、UI `64/64`、TypeScript、Lint `0/58`、Windows 前端 1,968 modules 构建通过。
- 桌面端 `go test . ./backend`、`go vet . ./backend`，CLI `go test ./...`、`go vet ./...`，Worker 语法和 `5/5` 测试通过。
- 版本漂移、gofmt、`git diff --check` 和仅包含受跟踪/待提交源码的合规快照通过；开发目录内的 `node_modules`、`dist`、运行日志和开发 CLI 继续作为忽略文件存在。
- Codex 浏览器完成 `1920x1080`、`1440x900`、`1024x768` 验收；页面宽度等于视口，可见控件无横向越界或文本截断，`1024x768` 设置弹窗完整位于窗口内。
- 真实点击验证文生图/图生图切换、设置、活动任务初始化拦截和 360 入口；最终恢复 `1239x930`、文生图和原 Profile，控制台 warning/error 为 0。
- 浏览器仍显示 API“已配置”和 14 个 Profile；用户原有 2 个排队记录、2 个失败入口和失败日志保持不变。

## 边界

- 没有点击生成、重试、取消、清理、API 连接测试、提示词调用或初始化。
- 没有读取或输出 API Key，没有修改稳定命名空间、迁移标记、旧版本或其他项目。
- 没有生成正式 Portable、发布附件、ZIP、标签或 Release，也没有推送 GitHub。
- 历史失败任务不会自动重试；如需验证真实 FHL 生成，应由用户另行明确授权付费路径。
