# Windows V2.0.4 连续池队列控制器

## 目标与边界

把连续池候选选择、启动占位、Profile/工作区游标、容量统计和 pump 单飞状态迁出主 Store，同时保持 `useStudioStore` 公共入口、任务记录、FHL 10 槽、每 API/总容量、Profile 快照、Toast、workspace session v1 和 Bridge v1 兼容。本批不迁移浏览器订阅、原生 Wails 事件生命周期、`launchOneJob`、`host.ts`、Bridge 或发布链。

## 实现与修复

- 新增 `studioStore.continuousPool.ts`，通过 `getState` 与 `runPumpPass` 依赖注入管理队列控制状态；主 Store 只保留传输、Profile 解析、任务提交和兼容转发。
- 候选继续只读取活动工作区引用的连续池排队任务，并排除 orphan、已有 job、`submitting` 和已占位任务。
- 工作区内按 `createdAt / slotIndex / id` 保持顺序，工作区之间按轮次交错；每次实际调度后把下一工作区游标移到刚处理工作区之后，避免总容量较小时旧工作区长期占先。
- Profile 游标继续驱动未分配任务的 API round-robin；已分配任务仍固定原 Profile，原生与浏览器批量 wave 共用相同工作区公平顺序。
- in-flight 继续统计 starting、submitting、running 和已有 job 的 queued 任务；取消后的 Wails 任务在 `settled` 前通过 `runningJobMeta` 保留容量，且不会与任务 jobId 重复计数。
- `reserveTaskStart()` 原子拒绝重复启动；pump 请求在单个 Promise 内合并，但 pass 运行期间的新请求会再执行一轮，不会丢失。
- reset 清空启动占位、Profile/工作区游标和待执行请求，并递增 generation 隔离仍在等待的旧 pass；初始化完成后的新 pump 可以独立启动。
- 第一次 Windows 构建发现 Promise 清理局部变量存在严格初始化顺序错误；改为显式 active Promise 清理后，构建和全量回归通过。

## 行为覆盖

- 6 条控制器测试覆盖 orphan 排除、启动占位防重、跨工作区公平、等待 `settled` 的取消容量、Profile/总容量上限、pump 单飞不丢请求和 reset 世代隔离。
- 原生 Store 测试新增启动失败可见回归，确认任务进入 `failed`、保留错误文本并打开结果网格。
- 调度器新增已分配任务保持 Profile、未分配任务继续 round-robin 的回归。
- 原 Store 中依赖内部函数位置和变量名的三组源码字符串断言改为控制器行为测试，仅保留公共接线与原生 launch claim 的兼容断言。
