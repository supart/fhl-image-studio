# Windows V2.0.4 跨运行时请求合约

## 目标与边界

为 Responses、Images、APIMart 和 RunningHub 建立同一份 JS/Go 请求合约夹具，直接验证生产请求构建器、最终 endpoint 和完整 JSON body。本批不调用真实 API，不修改公开 CLI 命令、Bridge v1、凭据、存储 namespace、任务生命周期或发布链。

## 实现

- 将 `shared/kernel/testdata/generation-request-contracts.json` 升级为 schema v2，用 8 个离线用例覆盖 Responses openai/compat、Images streaming/New API、APIMart generate/edit 和 RunningHub text/edit。
- 每个用例锁定最终 URL、JSON body type 和完整 body；只使用 `fixture-token-not-a-key` 及虚构上传 URL，不包含真实凭据。
- 前端提取 Images、APIMart、RunningHub 纯 payload builder，生产提交与 Node 测试共同调用；Responses 继续复用 shared kernel builder。
- Go 提取对应 payload builder 和统一 OpenAI endpoint helper；生产请求与 Go fixture 测试共同调用，APIMart 空图片列表固定序列化为 `[]`。
- 将 OpenAI Base URL 尾部 `/v1` 归一化收口到 shared JS helper 和 Go endpoint helper，修复 Worker、CLI Responses/Images 可能拼成 `/v1/v1/...` 的问题。
- APIMart/RunningHub 的非预设像素尺寸统一按最大边推导 1K/2K/4K；Go 最近比例改为与前端相同的对数距离和固定候选顺序，消除跨运行时漂移与 map 顺序不确定性。
- Worker `/kernel/generate` 改为只接受空值兼容或精确 `responses`；修复 `runninghub` 被旧 mode 归一化误判为 Responses 并错误代理的问题。

## 审计结论

- 专业 agent 确认原 schema v1 只完整覆盖 Responses，并发现 `/v1` endpoint、未知像素尺寸、比例距离和 Worker mode 的实际漂移；这些问题均由 schema v2 用例锁定并修复。
- JS 的显式 `partialImages=0` 表示关闭预览，CLI 的 `0` 仍表示使用默认值；这是现有入口语义差异。本批夹具使用共同值 1/2，不在没有“未指定/显式 0”区分接口时强行统一。
- Responses 的空白字符归一化差异未在本批改变，避免影响 verbatim 语义；规范输入已通过完整 wire body 比较。
- Images multipart edit 的文件字段和数量继续由现有运行时测试覆盖；共享夹具只比较各运行时都能等价表达的 JSON 请求。
